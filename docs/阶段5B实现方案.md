# 阶段 5B 实现准备（未启用）

日期：2026-10-16。本文是设计准备，不是已实现接口或法律规则。D-05 仍待用户明确选择；不得依据“继续”自动开启法定期间计算、确认或正式提醒。客户端 11A1 可以独立验收。

## 目标接口与数据边界

- 登记期间只写 DEADLINE_RULE 候选任务：proposedDueDate、规则版本、基准日、期间类型；dueDate 和确认者仍为空。普通任务 API 的删除和编辑保护保持。
- 单独的确认操作需要用户主动提交核对后的截止日与确认意图；服务端记录操作者、时间、规则版本并写审计。不能由后台计算、AI 或表单默认值自动确认。
- GET /deadlines/upcoming 仅查当前用户可访问案件的已确认、未删除期间，稳定按日期排序；未确认候选另列，不冒充已确认截止日。
- 站内提醒以受权限保护的通知列表交付；推送只留接口，不接真实短信、邮件或设备服务。标题/内容最小化，不把案情、描述、链接写入队列或日志。

## 规则配置待核对项

规则需 YAML 配置和不可变版本，运行前严格校验；在 D-05 确认前不发布有效规则包。原需求的 15/10 日、法院指定举证天数、届满前 30 日、生效日起两年都是待专业核对的候选模板，不是完整法律依据。

| 类型 | 实现前必须明确的输入/边界 |
|---|---|
| 上诉 | 判决/裁定类型、程序适用范围、有效送达起算、期间排除与节假日；不得只凭“送达日”自动确定 |
| 举证 | 法院实际指定期限/日期，避免把手输天数当统一法定规则 |
| 保全续封 | 明确届满日与提醒日的不同；不能把最初保全日直接当届满日 |
| 申请执行 | 明确生效日、特殊履行期限与法定例外；跨年/闰日处理需专业核验 |

日期工具可复用现有严格 YYYY-MM-DD 与北京时间边界。计算器保持纯函数、无数据库与网络；坏配置、未知规则和缺少输入必须失败，不回退到默认法律结论。节假日数据来源、覆盖年份和版本也须明确，不能用“周末”代替法定节假日或声称已核验。

## 提醒幂等与失败恢复设计

仅扫描已人工确认、TODO、未删除且父案件有效的记录。每小时扫描；进预警窗口后生成站内提醒。Redis 定时锁仅减少重复工作，数据库唯一提醒账本才是多实例重试的最终去重边界。

建议账本唯一键包含 taskId、确认截止日/确认版本指纹、windowDay；lastAlertedAt 只作摘要，不能单凭一个时间戳判定三个窗口或并发重试。提醒落库与 lastAlertedAt 更新同事务。数据库成功后外部推送失败不能重建另一条站内提醒。

过期/漏扫后的补发策略、改期重确认后旧通知的呈现、完成后恢复待办是否补提醒，均在实现前记录明确语义；不默默采用“每小时重发”或清空提醒历史。移除权限后不能继续读取旧通知；归属变更留阶段 9 一并核对。
