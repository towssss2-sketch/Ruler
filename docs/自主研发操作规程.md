# 自主开发执行与质量管控 SOP

## 一、操作闭环
1. **输入**：用户用中文写需求（见 `docs/需求卡片模板.md`）。
2. **拆分**：Codex 从需求、当前代码和原始 v3 制定最多一个 PR 的工作范围，记录前置依赖和验收点。
3. **实现**：直接修改仓库，编写测试、运行格式检查、类型检查、单测、e2e（能力不足时声明）。
4. **验证**：由 GitHub Actions 在全新 runner 上构建，杜绝“我电脑能跑”的环境污染。
5. **呈现**：生成中文 PR 验收说明，交付截图（可验证来源）、功能演示方法、APK/Windows ZIP（如果该任务触及客户端）。
6. **用户决定**：通过→合并；不通过→描述现象并附图，Codex 修复同一 PR，再走测试。不要自动合并有待验收事项的 PR。

## 二、质量分层
- L0 静态：格式、依赖锁、TS strict、Flutter analyze、敏感信息扫描。
- L1 单元：服务/纯函数/Provider/Widget，重点法定期限计算、权限、归集规则、RT 流水。
- L2 集成：PostgreSQL+Redis+MinIO，迁移、幂等、队列、权限、存储。
- L3 e2e：虚构账号登录→案件→上传→任务→读取；非生产环境。
- L4 设备：APK 在真实 Android 授权/后台限制/系统分享体验；Windows 执行文件预览与上传。
- L5 上线门禁：人工授权、独立安全评估、法定期间法律校验、隐私告知/合法性与第三方平台条款审查。

任何 PR 应列出各层 `PASS`/`FAIL`/`NOT_RUN`/`BLOCKED`，不可将 NOT_RUN 写成 PASS。仅绿灯 CI 不代表真实设备和法律合规完成。

## 三、禁止行为
- 不要给 AI/云运行环境传真实案件卷宗、短信验证码、未脱敏当事人信息。
- 不要把 API_KEY、OSS 密钥、数据库密码、邮件凭据写到代码或 GitHub 文件；使用仓库 Secrets/环境变量。
- 不要自动付款、租云服务器、提交 ICP 备案、启用真实收费接口、生产迁移、解除安全规则或自动合并主分支。
- 不要通过绕过验证码、人机校验或权限来获取法院平台文件。
- 不要将真实法律期限仅凭自动识别结果直接标记确定；须复核文书性质、送达日期、节假日和适用程序。

## 四、失败恢复
- CI 红：Codex 阅读失败日志→复现→修复→重跑；最多三轮自动尝试后明确阻塞原因，不要不断重复或消耗无限 token。
- 外部平台不可用：标为 BLOCKED，提供手动导入/系统分享兜底。
- 集成变更破坏历史功能：回退 PR 或 revert commit，恢复绿色版本后重试。
- 需求不明：可逆低风险选择写入假设，涉及高风险停止对应动作请求决策。

## 五、给用户的交付样例
**RULER 任务：新建案件**；状态：待验收。实现：可填写案号、案由和当事人。检查：22 个测试 PASS，0 FAIL；Actions 编号和链接。体验：下载 APK→登录虚构测试账号→新建案件→重新打开看是否保存。已知限制：尚未接入正式短信。决策：输入“通过”继续，或“不通过：点击保存时……”。
